# Plan: T014/T015 — Filtros por Rango para Columnas Financieras

## Recomendación de Experto: Opción 2 (Selector de Columna + 2 Inputs)

### ¿Por qué Opción 2 y no las demás?

| Opción | Problema |
|--------|----------|
| **Opción 1** (Dialog con 16 inputs) | Sobrecarga cognitiva extrema. El usuario debe escanear 16 campos para encontrar el que necesita. Abre un modal solo para filtrar — demasiada fricción para una acción común. |
| **Opción 2** (Selector + Mín/Máx) | **Ganadora.** Mantiene la barra de filtros limpia (solo 3 elementos nuevos). El usuario selecciona la columna y Define el rango. Consistente con UX de software financiero. Filtrado de a una columna a la vez es el caso de uso más común. |
| **Opción 3** (Omitir) | Viola FR-007 del spec. No es aceptable post-MVP si el feature está planeado. |


## Flujo de Datos Completo

```
Usuario selecciona columna + escribe rango
    ↓
State: filter_financiera_campo, filter_financiera_min, filter_financiera_max
    ↓
load_liquidaciones() extrae los valores
    ↓
servicio_financiero.listar_liquidaciones_paginado(..., financiera_campo, min, max)
    ↓
repositorio_liquidacion_postgres agrega WHERE condition dinámica
    ↓
SQL: WHERE l.CAMPO >= %s AND l.CAMPO <= %s
    ↓
Resultados filtrados → UI se actualiza
```

## Verificación

1. **Unit**: Verificar que `active_filter_count` incrementa al aplicar filtro financiero
2. **Integration**: Seleccionar "Gastos Administración", poner min=100000, max=500000 → solo mostrar liquidaciones en ese rango
3. **Edge cases**:
   - Solo min (max vacío) → mostrar todo >= min
   - Solo max (min vacío) → mostrar todo <= max
   - Ambos vacíos → no filtrar
   - Columna vacía → ignorar min/max
   - Valores con formato colombiano (punto como separador de miles)
4. **Limpiar**: Botón "Limpiar" debe resetear los 3 campos financieros
5. **Mobile**: Verificar que los 3 inputs se apilan correctamente en el drawer
6. **Exportación**: Verificar que T016 (export payload) incluye los campos financieros
