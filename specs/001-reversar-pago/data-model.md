### State Transitions (Payment Reversal)

```
Pagada ──[reversar_pago]──► Aprobada
   │                          │
   │                          ├── FECHA_PAGO = NULL
   │                          ├── METODO_PAGO = NULL
   │                          ├── REFERENCIA_PAGO = NULL
   │                          ├── PAGADA_POR = NULL
   │                          └── PAGADA_EN = NULL
```

**Guard condition**: `ESTADO_LIQUIDACION = 'Pagada'`
**Idempotency**: If state is already 'Aprobada', operation is a silent no-op.

### Audit Records Generated Per Reversal

For a single payment reversal, the following AUDITORIA_CAMBIOS records are generated:

| # | CAMPO_MODIFICADO | VALOR_ANTERIOR | VALOR_NUEVO |
|---|------------------|----------------|-------------|
| 1 | ESTADO_LIQUIDACION | Pagada | Aprobada |
| 2 | FECHA_PAGO | 2026-01-15 | NULL |
| 3 | METODO_PAGO | Transferencia Electrónica | NULL |
| 4 | REFERENCIA_PAGO | TX-12345 | NULL |
| 5 | PAGADA_POR | admin | NULL |
| 6 | PAGADA_EN | 2026-01-15T10:30:00 | NULL |
| 7 | MOTIVO_REVERSION | NULL | [user-provided motivo] |

Records 1-6 are auto-generated by the existing trigger on LIQUIDACIONES.
Record 7 is inserted explicitly by the application code.

## Validation Rules (from FR)

- FR-001: Only liquidations with `ESTADO_LIQUIDACION = 'Pagada'` can be reversed
- FR-004: Motivo must be >= 10 characters
- FR-009: If `ESTADO_LIQUIDACION != 'Pagada'`, operation is silent no-op
- FR-014: Each reversal operation is identified by the combination of (ID_LIQUIDACION + timestamp + usuario)
